# Phase 2 — Test Opryn and knowledge applicability

Implemented and released to production with explicit user approval on 2026-09-16. The four Phase 2 migrations are applied. No test fixtures or synthetic knowledge records were inserted into production.

## Product behavior

- `/app/knowledge/test`: owner/admin response simulation using the existing embedding, authorized retrieval, trust gate and company-answer service. Employee/new-hire perspectives use a selected actual member. Connected-AI/support-bot/call-agent perspectives use an actual external AI connection and its current allowed sources, scopes and existing Premium subscription entitlement. Labels do not grant access or imply an external adapter was contacted.
- Results: answered, unknown, conflict, needs clarification or restricted. Include the tested question, real generated answer when verified, access description and cited approved source versions. Recheck access, roles, trust and versions after generation; withhold the answer if they changed.
- Saved tests: expected outcome and optional approved source, explicit save/run/rerun/delete, latest run evidence and a rerun indicator when cited/expected versions change or are withdrawn. Exact outcome/source matching is **not** a model judgment of answer correctness. Up to 50 recent saved tests; up to 200 current source choices.
- Entry points: individual Knowledge detail, Knowledge Health, AI connection detail, controlled Guide destination. No extra top-level navigation.
- Applies to: optional roles, departments, regions, locations, customer types, customer plans, products, channels and inclusive effective dates. Empty scope is global. Values match exactly ignoring case/outer whitespace; no guessed geographic hierarchy or fuzzy role mapping. Alternatives within a dimension are OR; dimensions combine with AND. Date comparisons use UTC.
- Scope is applicability, not authorization. Member role and channel derive from real membership/surface. External role context is only a simulation/application context; actual connection permissions still gate every candidate. Missing required context fails closed before model input. Ask has optional business-context inputs; API/MCP accept validated typed context. Slack/Teams currently derive member/channel but do not collect arbitrary regional context through a new conversational interview.
- Pending proposals: edit scope with exact revision/time checks. Approved items: editing scope creates a proposal; canonical approval creates a new immutable version, retaining the old scope and source history. Published scope cannot be silently changed without a version increment. Existing updates generated by the application proposal builder inherit the prior approved scope.
- Rechecks use original question context, actual current membership/connection permissions and a final SQL scope check before certifying an answer. External intake separates different applicability contexts while attaching repeated identical contexts.
- Normal loading uses text; the existing Thinking Orb appears during real AI test runs. Existing Motion wrappers provide local transitions and reduced-motion behavior. Current icons, billing, integrations and homepage remain unchanged.

## Schema / rollout

Four additive migrations, in order:

1. `20260916030000_knowledge_scope_and_test_cases.sql`: validated JSON scope/context, organization-scoped saved tests, admin-only browser reads, server-only writes, exact-revision scope proposal functions, published-scope guard.
2. `20260916031000_versioned_proposal_scope.sql`: existing atomic canonical approval persists previous/new scopes and bumps proposal revision on scope edits. No second approval workflow.
3. `20260916032000_scoped_gap_intake.sql`: server-only external intake gains an optional validated context parameter; default preserves older callers.
4. `20260916033000_scope_recheck_guard.sql`: commit-time scope validation on the existing durable verification queue.

Deployment needs explicit approval and a controlled migration/code rollout. New code requires these columns/functions. Do not deploy code alone. Do not drop columns or saved/customer knowledge to roll back. After scoped knowledge has been approved, rolling back to old scope-unaware answer code is unsafe: retain the scope-aware retrieval guard or withdraw affected scoped items through the canonical archive lifecycle before rollback. Existing data starts with global `{}` scope, so additive migrations do not reinterpret current rules.
